# Session Objective Protocol

## 文件命名规则

Objective 文件存放于 `.ai-objectives/` 目录，命名格式为：

```
<YYYYMMDD_HHmm>_<short-slug>.md
```

- 时间取创建时刻（精确到分钟）
- `short-slug` 为 2-4 个英文单词的短描述，用连字符连接，从核心目标中提炼（如 `add-retry-logic`、`user-auth-refactor`）
- 示例：`20260408_1430_add-retry-logic.md`

文件内部使用 frontmatter 记录元信息：

```yaml
---
status: active   # active | completed | archived
created: 2026-04-08T14:30
objective: 一句话核心目标
---
```

## 发现与绑定

每次会话开始时（或识别到用户开始多步骤工作流时），先扫描 `.ai-objectives/` 目录下所有 `.md` 文件：

1. **存在 `status: active` 的文件时**：
   - 读取其核心目标，向用户确认："发现一个进行中的目标：`<核心目标>`（文件：`<文件名>`），是否继续这个任务？"
   - 用户确认后，绑定该文件为当前会话的 objective，后续所有读写都针对此文件
   - 用户否认后，询问是要创建新的 objective 还是要归档/清除旧的
   - 如果存在多个 active 文件，列出所有文件及其核心目标，让用户选择
2. **不存在 active 文件时**：进入"创建"流程

**绑定后不得切换**：一旦会话绑定了某个 objective 文件，在该会话内不得自行切换到其他 objective 文件。如果用户的对话方向明显偏离当前 objective，应提示用户而非静默切换。

## 创建

当需要创建新的 objective 时：

1. 先与用户确认核心业务目标（一句话描述"最终要达成什么"）
2. 列出需要完成的步骤（从命令组结构、specKit 流程、或用户描述中推断）
3. 记录已知的关键约束
4. 按命名规则生成文件名，创建文件，结构如下：

```markdown
---
status: active
created: <ISO 时间>
objective: <一句话核心目标>
---

## 核心目标
[一句话描述业务目标]

## 执行进度
- [ ] 步骤1
- [ ] 步骤2
- ...

## 关键约束
### 业务约束
- [来自需求/spec/clarify 的约束]
### 技术约束
- [来自代码/配置/环境发现的约束]
### 流程约束
- [来自用户要求的执行方式偏好]
```

5. 创建完成后，**必须**向用户回显确认信息（不可省略）：
   - 一句话复述核心目标，并询问："这个理解是否准确？"
   - 说明已创建的文件路径，告知该文件会在整个任务过程中帮助保持目标清晰、进度可追踪；任务完成后会提示归档或清除
6. 若用户尚未确认目标表述，**不得**继续后续执行步骤

创建文件前，检查项目根目录的 `.gitignore` 是否已包含 `.ai-objectives/`。如果没有，自动追加一行 `.ai-objectives/` 到 `.gitignore` 末尾。

## 生命周期

- **完成时**：将 frontmatter 中 `status` 改为 `completed`，提示用户是否归档
- **归档时**：将 `status` 改为 `archived`，文件保留不删除（作为历史记录）
- **用户要求清除时**：可以删除文件

## 更新触发条件（必须主动执行，不等用户要求）

- **执行下一步之前（前置门控）**：检查 objective 中对应步骤的 checklist 粒度是否与当前已知的执行计划一致。若不一致（如某步骤已可细分为多个子步骤），先更新 checklist 再执行。此条优先于所有事后触发条件。
- **完成一个步骤后**：立即勾选对应 checkbox，不要累积多个步骤再批量更新
- **发现新的关键约束时**：立即追加到约束列表。包括但不限于：覆盖率/扫描排除规则、CI/CD 配置、依赖版本限制、代码风格强制规则、环境差异等**从代码或配置中查到的事实**，以及回答用户问题过程中获得的技术结论。
- **用户给出新的执行约束或编码规范时**：立即追加到关键约束列表
- **澄清问题得到结论时**：将结论同步到 objective（不仅仅写入 spec 或其他文档）
- **步骤状态变更时**（完成→未完成、需重做等）：立即更新对应 checkbox 状态
- **步骤结构变更时**（优先级高于状态变更）：当某个粗粒度步骤需要拆分为多个子步骤时（如"代码实现"拆为 specKit 的多个阶段），立即将原 checkbox 替换为细粒度的子步骤列表，再继续执行。不得在粗粒度 checkbox 上直接推进。
- **新增待确认问题时**：追加到待确认区块
- **外部确认问题得到答复时**：从待确认移到已确认，并更新约束
- **可用能力变化时**：当新的工具、MCP server、skill 变为可用（如插件安装、MCP 连接成功）或不可用（如工具报错、权限丢失）时，评估其对当前执行计划的影响。若影响了步骤分解或执行路径，立即更新对应阶段的 checklist。

## 检查点规则

每完成一个阶段性步骤（specKit stage、命令组中的一个命令、或任何有明确产出的子任务）前，暂停并回顾：
1. 本步骤中是否产生了新的约束或事实性结论？
2. 关键约束列表是否需要更新？
3. 是否有信息应同步到 objective 但被遗漏了？

此检查与前置门控互补：前置门控检查 checklist 粒度，检查点检查约束完整性。

## 禁止行为

- **不得自行修改核心目标**——只有用户确认后才能改
- 对于 Agent 无法执行的步骤（如平台操作、线下沟通），**必须**标记为 `[ ] ⚠️ 需人工执行：<具体操作>`，且**不得**标记为 `[x]`
- 当 checklist 中仍存在未完成项（包括线下步骤）时，**不得**声明整体步骤或整体目标已完成
- 结束时如果仍存在未完成的线下步骤，**必须**在总结中列出待办清单，并明确提醒用户后续跟进

## 主动建议

- 用户提出新约束或反复强调某个要求时：建议"要不要把这条加进核心目标？"
- 执行中发现某个约束与实际情况矛盾时：建议"这条约束可能需要调整，要更新核心目标吗？"
- 用户明确改变方向时：建议"目标似乎有变化，要不要更新核心目标？"
- checklist 全部完成时：提示"核心目标已全部达成，是否标记完成并归档？"
- 当前对话与已绑定的 objective 内容明显无关时：提示用户，由用户决定是继续当前 objective、归档后新建、还是并行新建

## 执行原则

- 你可以自由决定每一步怎么做，但不能自行跳过 checklist 中未完成的步骤
- 如果认为某步骤确实不需要，向用户说明并获得确认后才能跳过
- 如果某个 Gate 条件因客观原因无法验证（如缺少工具、配置不全），**不得**直接标记为通过，也**不得**用定性判断替代通过结论。**必须**执行：
  1. 标记为 `BLOCKED`，并写明无法验证的具体原因
  2. 向用户汇报，由用户明确决策：跳过 / 修复环境后重试 / 降级为手动验证
  3. 将用户决策记录到当前 objective 文件的约束列表中
- 主动发现和利用可用的 MCP、skill 来丰富产出质量
- 每一步的产出都是业务知识库的一部分，即使看起来冗余也有保留价值
- 约束路由规则：用户给出的约束，凡与当前任务执行相关的，一律追加到关键约束列表。无法判断相关性时，优先写入（漏写代价高于多写）。
